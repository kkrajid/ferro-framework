# Migrations

Migrations keep the database schema in step with your models, as in Django: you change models,
Ferro writes a migration file describing the change, and `ferro migrate` applies it.

## Everyday workflow

```bash
ferro makemigrations          # compare models with migrations/, write the next file
ferro migrate                 # apply files not yet applied
ferro migration status        # list files and whether each is applied
ferro rollback                # revert the last applied migration
```

All commands read the database URL from `.env` / `FERRO_DATABASE_URL` / `--database-url`, use
`migrations/` (or `--migrations-dir DIR`) and take an optional `module:app` target (default
`app:app`), which they import so that every model is registered.

```text
Created migrations/0002_add_note_color.py
  - add column color to note
```

Commit migration files together with the model change. Every environment (colleagues, CI,
production) then runs `ferro migrate` and ends up with the same schema.

## What a migration looks like

```python
"""Generated by Ferro 0.5.0rc1 on 2026-10-12 09:30 UTC."""

from ferro.migrations import Migration, ops

migration = Migration(
    dependencies=["0001_initial"],
    operations=[
        ops.AddColumn("note", ops.Column("color", "String", max_length=20), default="yellow"),
    ],
)
```

Files are plain Python: read them in code review, edit them when the generated guess is wrong.

| Operation | Purpose |
|---|---|
| `ops.CreateTable(table, [ops.Column(...), ...])` | new model |
| `ops.DropTable(table)` | removed model |
| `ops.RenameTable(old, new)` | renamed table |
| `ops.AddColumn(table, column, default=...)` | new field (`default` back-fills existing rows) |
| `ops.RemoveColumn(table, name)` | removed field |
| `ops.AlterColumn(table, column)` | changed type, length, null, unique |
| `ops.RenameColumn(table, old, new)` | renamed field (keeps the data) |
| `ops.CreateIndex(table, columns, name=None, unique=False)` / `ops.DropIndex(table, name)` | indexes |

`ops.Column(name, kind, null=False, unique=False, primary_key=False, auto=False,
max_length=None, max_digits=None, decimal_places=None, references="table.column",
on_delete="cascade")`.

## Rules and safety

- **Each migration runs in one transaction** on SQLite and PostgreSQL: it applies completely or
  not at all. A failing migration leaves the database as it was.
- **New non-null fields need a constant default** to fill existing rows
  (`models.String(max_length=20, default="yellow")`). Otherwise `makemigrations` stops and
  suggests: give a default, allow `null=True`, or add the field nullable first and make it
  required in a later migration after filling it.
- **Renames are not guessed.** A renamed field is generated as remove + add, with a warning. To
  keep the data, replace the two operations with `ops.RenameColumn("table", "old", "new")`.
  Same for tables (`ops.RenameTable`).
- **Making a column non-null** fails cleanly if rows still contain NULL; fill them first.
- **SQLite** cannot alter columns in place; Ferro rebuilds the table, keeping rows, indexes and
  the id sequence.
- **History check**: applied migrations are recorded in the `ferro_migrations` table. If the
  files and the history disagree (a file deleted or reordered), commands stop with an
  explanation instead of guessing.

## Rolling back

```bash
ferro rollback                      # the last one
ferro rollback --steps 3
ferro rollback --to 0004_add_price  # keep 0004 applied, revert everything after it
ferro rollback --to zero            # revert everything
```

Every reverse step is checked before anything is changed. Rolling back a `DropTable` or
`RemoveColumn` recreates the structure, not the deleted data — restore data from a backup.

## In CI and deployments

```bash
ferro makemigrations --check        # exit 1 when models changed but no migration was written
```

Run it in CI so a model change can never reach production without its migration.

Deploying: run `ferro migrate` **once per release, before** the new code serves traffic
(a release command, a Kubernetes Job, a step in your deploy script — see the
[deployment guide](../deployment.md)). For zero-downtime deploys, keep each migration compatible
with the previous release's code: add columns as nullable or with defaults, and remove columns
one release after the code stopped using them.

## Other commands

```bash
ferro makemigrations --name add_indexes      # choose the file name
ferro makemigrations --empty --name manual   # an empty file to fill by hand
ferro db create-tables                       # create missing tables without migrations (experiments)
```

`ferro db create-tables` and `ferro.db.create_tables()` (used by tests) create tables directly
from the models; never mix them with migrations on the same database.

## Limits

- No data migrations (Python code inside migrations) yet: transform data with a script run
  between two migrations, or in SQL through your database client (`ferro db shell`).
- Migrations are linear (one chain); after merging two branches that both added a migration,
  roll back and delete one of them (where it was applied), then run `ferro makemigrations`
  again.
