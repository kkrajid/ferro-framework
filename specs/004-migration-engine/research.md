# Research: Migration Engine

**Feature**: [spec.md](spec.md) | **Date**: 2026-10-10

## R1. Where the logic lives

- **Decision**: new crate `crates/migrations` (`ferro-migrations`), pure Rust: `Operation`,
  `ColumnDef`, `SchemaState` (replay/apply with validation), `diff(state, models)`,
  `reverse(op, state_before)`, `compile(dialect, state_before, op) -> Vec<Statement>`. Python
  (`ferro.migrations`) loads/writes migration files, post-processes back-fill defaults (they are
  Python values from field declarations) and drives the CLI.
- **Rationale**: constitution I/III — schema management in Rust; files and prompts are DX.

## R2. File format (clarified)

```python
"""Generated by Ferro 0.1.0 on 2026-10-10 09:30 UTC."""

from decimal import Decimal

from ferro.migrations import Migration, ops

migration = Migration(
    dependencies=["0001_initial"],
    operations=[
        ops.AddColumn("product", ops.Column("stock", "Integer"), default=0),
        ops.AlterColumn("product", ops.Column("price", "Decimal", max_digits=12, decimal_places=2)),
    ],
)
```

Operations serialize to dicts for the native core (`{"op": "add_column", ...}`); the writer
renders dicts back to code. Values in files: int, float, str, bool, None, `Decimal`, `UUID`,
`datetime.*`, lists/dicts of those.

## R3. Diff rules

- Managed tables are those in the replayed state. Model tables missing from the state →
  `CreateTable` (+ `CreateIndex`); state tables without a model → `DropTable` (warning).
- Columns compared by column name: added → `AddColumn`; removed → `RemoveColumn`; definition changed
  (kind with parameters, null, unique) → `AlterColumn`. Primary-key/auto changes → error.
- Indexes named `<table>_<column>_idx` for `index=True` non-unique columns; differences →
  `CreateIndex`/`DropIndex`. Indexes on a removed column are dropped first.
- Order in one migration: `CreateTable`; per table `DropIndex`, `RemoveColumn`, `AddColumn`,
  `AlterColumn`, `CreateIndex`; `DropTable` last.
- Rename heuristic: in one table, exactly one removed and one added column of the same kind → a
  warning suggesting `RenameColumn`.

## R4. SQL per database

| Operation | PostgreSQL | SQLite |
|---|---|---|
| CreateTable / DropTable | `CREATE TABLE` (same DDL as create-tables) / `DROP TABLE` | same |
| RenameTable | `ALTER TABLE a RENAME TO b` | same |
| AddColumn nullable | `ALTER TABLE ADD COLUMN` (+ `ADD CONSTRAINT .. UNIQUE`) | `ADD COLUMN` if not unique, else rebuild |
| AddColumn non-null + default | add nullable; `UPDATE t SET c = $1`; `SET NOT NULL` | rebuild with `SELECT ..., ?` back-fill |
| RemoveColumn | `DROP COLUMN` | rebuild |
| AlterColumn | `TYPE .. USING c::type`, `SET/DROP NOT NULL`, `ADD/DROP CONSTRAINT <t>_<c>_key` | rebuild |
| RenameColumn | `RENAME COLUMN` (+ rename its index) | `RENAME COLUMN` (+ recreate its index) |
| CreateIndex / DropIndex | `CREATE INDEX` / `DROP INDEX` | same |

SQLite rebuild: `CREATE TABLE "__ferro_new_<t>"` with the target definition, `INSERT INTO new
(cols) SELECT cols FROM t` (new non-null columns get a bound back-fill parameter), `DROP TABLE t`,
`ALTER TABLE new RENAME TO t`, recreate indexes — inside the migration's transaction. Explicit
`id` values keep the AUTOINCREMENT sequence correct.

Both databases support transactional DDL, so each migration (operations + history row) runs as one
`Batch` job.

## R5. Reversal

`reverse(op, state_before)`: CreateTable↔DropTable (definition and indexes from the state),
AddColumn→RemoveColumn, RemoveColumn→AddColumn (needs a back-fill for non-null columns: the
operation's recorded `default`; otherwise irreversible), AlterColumn→AlterColumn(old definition),
RenameColumn/RenameTable swapped, CreateIndex↔DropIndex. Rollback first computes every reverse
operation; if any is irreversible nothing runs.

## R6. Cached statements after DDL (FR-014)

PostgreSQL reports `cached plan must not change result type` (SQLSTATE 0A000) when a cached
prepared statement refers to a changed table: the worker clears its statement cache and retries the
job once. SQLite re-prepares automatically after schema changes.

## R7. History

`CREATE TABLE IF NOT EXISTS "ferro_migrations" (id <auto key>, name varchar(255) NOT NULL UNIQUE,
applied_at varchar(32) NOT NULL)`; names read in `id` order. The unique name prevents duplicate
application by concurrent `migrate` runs (the second transaction fails and rolls back).
